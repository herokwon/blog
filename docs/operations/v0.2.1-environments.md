# v0.2.1 Environment Separation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax. Execution requires review of this plan; this document does not authorize external configuration changes.

**Status:** `Planned`.

**Goal:** Separate Local, Preview, and Production while preserving exact-candidate production promotion and enabling the full Admin lifecycle on Preview.

**Architecture:** Keep the existing `blog` Worker/D1 as Production and add `blog-preview` Worker/D1. Build each release candidate once and upload the same application artifacts with different runtime bindings. Deploy the returned Preview Version ID at 100% traffic; keep the Production candidate undeployed. Local development uses Preview-oriented settings with persistent local D1; automated tests use isolated disposable local databases.

**Tech Stack:** SvelteKit 3, adapter-cloudflare 8, Wrangler 4, D1, Drizzle, Cloudflare Access, GitHub Actions, Node 26, pnpm 12.

**Spec:** [Deployment](../architecture/deployment.md), [Security](../architecture/security.md), [Database foundation](../architecture/database-foundation.md), [ADR 0004](../adr/0004-isolate-preview-worker-and-d1.md).

This plan covers environment separation and environment-aware Admin controls.
The [authoring plan](v0.2.1-authoring.md) defines overall priorities and implements
recovery, layout, CSP diagnosis, and logout. Task 6 collects shared remote
acceptance evidence after both plans' implementation tasks pass.

## Global Constraints

- Preserve the existing Production database ID, data, domain, and migration history.
- Preview must have no Production D1 binding or Production custom-domain route.
- Keep application binding names `DB` and `ASSETS` identical across environments.
- Only the Preview default Worker URL and Production domain permit deployed Admin writes; individual Version URLs remain read-only.
- Retain verified JWT authentication, exact Origin checks, local-bypass restrictions, strict CSP, and no-store behavior.
- Preview persists across uploads; no automatic reset, reseed, or Production data copy.
- Promotion selects the exact Production candidate for final release head SHA and release annotation; it never rebuilds or substitutes an older candidate.
- Hotfixes remain Production-only; release synchronization prepares a new pair.

## Review Focus

1. A copied Preview config accidentally targets Production D1/domain: reject before any remote command (Task 1).
2. Preview deployment changes during acceptance or a stale workflow retries: preserve source identity and require final-head revalidation (Tasks 3 and 6).
3. One upload succeeds and the other fails/cancels: retain each confirmed outcome without claiming rollback (Task 4).
4. Preview JWT or Origin is reused against Production: reject before DB mutation (Task 5).
5. A later Preview migration affects older versions: document current-schema compatibility and never treat a version switch as DB rollback (Task 6).

## Dependency Order

Task 1 establishes targets; Task 2 consumes them. Task 3 consumes both, Task 4
reports Task 3, and Task 5 verifies the deployed request boundaries. Task 6
requires Tasks 1–5 and the separately implemented authoring/logout changes for
the complete v0.2.1 release acceptance.
