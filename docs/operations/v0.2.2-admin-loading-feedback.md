# v0.2.2 Admin Loading Feedback

Scope: [Issue #83](https://github.com/herokwon/blog/issues/83), combining display timing and Admin-wide loading coverage in one implementation branch, `codex/admin-loading-feedback`, based on `5075285`.

## Timing and Completion Policy

All existing indicator scopes use a **200ms display delay**, replacing 180ms.
Requests and processing guards start immediately. Short work cancels its pending
indicator; message changes do not restart a running delay. Work includes required
revalidation and valid-page correction; authoring also retains processing feedback
through its own destination load.

The **400ms minimum feedback visibility** candidate is satisfied by existing
nonblocking result notices, not by holding a spinner or overlay. Success remains
visible for five seconds (paused on hover/focus); error/conflict/uncertain guidance
is persistent. Explicit dismissal and navigation still consume notices normally.
No extra minimum-processing timer or second success message is introduced.

When processing actually ends, remove the pending visual and processing-only
locks immediately, apply the result, and present accurate guidance. Keep state
restrictions required by read-only, conflict and uncertain outcomes. A confirmed
mutation followed by failed refresh says that the operation completed but the
latest view could not be loaded. An observed state is not confirmed request
success and uses the existing uncertain notice presentation.

Logout shares the display delay because it uses the same pending component, but
verified departure is never delayed. Its result is the returned home page; a
failure uses the existing persistent notice and focused retry. Cloudflare Access
login-page or cross-document blank-screen changes are excluded.

### Timing Comparison

The old 180ms threshold exposed a loader before the 199ms test boundary. The
candidate 200ms threshold suppresses that case while still showing pending work
at 200ms. It is a project policy, not a standard or a proven perceptual optimum.

Controlled-clock browser cases compare completion at 100, 199, 200, 201, 800 and
2000ms. They check suppression before the threshold, indication after it,
immediate results/unlock without advancing the clock, and visible results 400ms
later. Component checks cover cancellation/retry, message transitions and
disposal. Desktop/mobile and reduced-motion inspection complement the clock
checks; these do not constitute physical-device or remote-latency measurements.

Each overlay's accessible status remains outside inert content. List headings
stay outside the list overlay; their existing guards still apply. Navigation
overlays cover the workspace, including its heading, while the session header
is locked separately. Mutation-driven navigation keeps its already-active input
overlay rather than introducing a second workspace overlay.

Region overlays retain their complete bounds, but their status block is sticky
within the region around the viewport center. A long table or mobile card list
must not move the spinner/message below the visible screen. This uses CSS only;
it adds no scroll listeners or timing state. Long-list top/scrolled cases cover
both widths in `loading-viewport.e2e.ts`.

### Independent Review and Fix

A fresh-context, read-only review of `5075285..565e340` found one P2 issue:
dismissing observed-result guidance during a slow authoring destination load
could recreate an empty-summary persistent notice when navigation completed.
No critical or minor findings were reported. Other processing, refresh, timing
and result-classification invariants had no actionable findings.

The author reproduced the dismissal/release sequence in a browser test (RED),
then guarded destination forwarding with the still-present message. Both normal
observed-result delivery and dismissal/no-replay cases passed (GREEN). This
preserves explicit dismissal without changing result classification or adding
another timer. The fix is verified by tests, not a second independent review.

The reviewer did not assess real screen-reader announcement timing, physical
devices or remote Access behavior; those are not claimed from DOM/local tests.
Local review and test artifacts are retained in
`.wrangler/admin-loading-feedback/`.

### Implementation Decisions and Limits

- Existing five-second/persistent notices satisfy the 400ms feedback comparison
  target. There is no additional minimum-processing timer; an omitted completion
  path was the risk addressed by the full action audit and observed/reload tests.
- Navigation uses SvelteKit's existing state and error handling. No new navigation
  subsystem is introduced; framework-level failures remain distinct from a
  mutation failure, with existing loader-error checks retained.
- New-post navigation can load code without a page data request. Tests hold both
  code and data resources and use bounded request-start checks; a prefetched
  resource cannot silently produce a passing held-request assertion.
- Region status is sticky within its existing overlay to remain visible on long
  lists. Its position differs from the previous full-region center; desktop,
  mobile, scroll and authoring-geometry checks cover that tradeoff.
- Legacy hover/menu and silent-observed expectations were adjusted to the approved
  policy. Their input, navigation, cursor, retry and revision checks remain.
- Execution used PowerShell-native plan/ledger bookkeeping in this Windows
  checkout. Shared-file implementation preceded focused implementation/test/docs
  commits; task-specific RED/GREEN evidence and the final whole-branch review
  checked that intermediate working-diff tradeoff.

The implementation is committed locally. PR creation, merge and deployment are
separate delivery steps; this record does not claim that any of those occurred.

## CI Navigation Synchronization Follow-up (Issue #87)

Release PR #85 and version PR #86 each had a navigation-overlay E2E failure
that passed on an unchanged-checkout retry. Controlled delayed-bootstrap
experiments reproduced the same symptom: `page.goto()` returned before the
client router was ready, and the test's broad node-module interceptor could
then block hydration itself. A native document navigation satisfied the broad
request-start flag without producing the application's navigation overlay.
Historical CI traces were not uploaded, so their exact event order remains
unverified; the synchronization defect was reproduced locally.

Navigation tests now confirm a real hydrated post-menu interaction before
installing destination gates. Data-loading destinations hold their exact path
and query; the code-only new-post destination resolves its module from the
built server manifest. The tests check resource type and reject document
navigation, retaining the existing overlay, inert, and settlement assertions.
Desktop and mobile pagination/trash cases explicitly hold the initial app
module until after the load event to cover slow bootstrap. No fixed sleep,
network-idle readiness requirement, assertion-timeout increase, or test retry
is introduced. CI retains failure screenshots, traces, and error contexts for
seven days when available.

The application, database schema, and deployment behavior are unchanged.

Local verification on 2026-10-22: the new desktop pagination/trash regressions
first failed with the original missing-overlay assertion. After the correction,
all 14 navigation cases passed, then passed 42/42 in three repetitions using
two workers. `pnpm check` reported zero errors/warnings; lint and diff checks
passed. The full `pnpm test` run passed 82 workflow, 484 unit/component, and
256 E2E tests, including the build. Independent review found no actionable
issue. Remote CI execution and failure-artifact upload remain unverified until
the change is published.

## Acceptance Boundaries

No API/schema/migration, Cloudflare Access login change, remote mutation or
Production deployment is included. Local JWT/Access fixtures do not prove real
Access login/logout or physical-device keyboard acceptance. The timing policy
does not claim to optimize actual network latency.
