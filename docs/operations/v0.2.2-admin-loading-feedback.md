# v0.2.2 Admin Loading Feedback

Scope: [Issue #83](https://github.com/herokwon/blog/issues/83), combining display timing and Admin-wide loading coverage in one implementation branch, `codex/admin-loading-feedback`, based on `5075285`.

## Timing and Completion Policy

All existing indicator scopes use a **200ms display delay**, replacing 180ms.
Requests and processing guards start immediately. Short work cancels its pending
indicator; message changes do not restart a running delay. Work includes required
revalidation and valid-page correction; authoring also retains processing feedback
through its own destination load.

The **400ms minimum feedback visibility** candidate is satisfied by existing
nonblocking result notices, not by holding a spinner or overlay. Success remains
visible for five seconds (paused on hover/focus); error/conflict/uncertain guidance
is persistent. Explicit dismissal and navigation still consume notices normally.
No extra minimum-processing timer or second success message is introduced.

When processing actually ends, remove the pending visual and processing-only
locks immediately, apply the result, and present accurate guidance. Keep state
restrictions required by read-only, conflict and uncertain outcomes. A confirmed
mutation followed by failed refresh says that the operation completed but the
latest view could not be loaded. An observed state is not confirmed request
success and uses the existing uncertain notice presentation.

Logout shares the display delay because it uses the same pending component, but
verified departure is never delayed. Its result is the returned home page; a
failure uses the existing persistent notice and focused retry. Cloudflare Access
login-page or cross-document blank-screen changes are excluded.

### Timing Comparison

The old 180ms threshold exposed a loader before the 199ms test boundary. The
candidate 200ms threshold suppresses that case while still showing pending work
at 200ms. It is a project policy, not a standard or a proven perceptual optimum.

Controlled-clock browser cases compare completion at 100, 199, 200, 201, 800 and
2000ms. They check suppression before the threshold, indication after it,
immediate results/unlock without advancing the clock, and visible results 400ms
later. Component checks cover cancellation/retry, message transitions and
disposal. Desktop/mobile and reduced-motion inspection complement the clock
checks; these do not constitute physical-device or remote-latency measurements.

## Admin Action Inventory

| Action                                             | Previous coverage or gap                                                            | Resulting scope and lifecycle                                                                                              |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Normal-list publish/republish/archive/delete       | Local status; no list-region overlay                                                | Region covers `section.admin-content`, including filters, items and pagination, through mutation/refresh/page correction   |
| Trash restore                                      | Shared local list status                                                            | Same region coverage; removal and empty trash retain correct completion guidance                                           |
| Detail publish/republish/archive/delete/restore    | Existing local processing block                                                     | Remains local; shared delay and result policy; sibling navigation/session guards remain                                    |
| Create draft/save/publish/retry                    | Input overlay; mutation could finish before destination load                        | Caller-owned submission state keeps input overlay and guards continuous through destination loading                        |
| Latest-content reload                              | Existing input overlay; old conflict remained while waiting and success was silent  | Clear prior result at start; preserve input on failure; announce successful replacement through existing success notice    |
| Filter/pagination                                  | Route data could wait without application feedback                                  | Existing SvelteKit `navigating` state drives workspace-region feedback                                                     |
| List/detail/new/edit/cancel and history navigation | Same route-wait gap                                                                 | Workspace feedback for pending in-app Admin navigation; native links, return context and dirty-navigation decisions remain |
| New-post module loading                            | No page-specific server data request                                                | Navigation indicator also covers the router's code-module load; no dummy request or artificial wait                        |
| Observed mutation recovery                         | Some paths silently removed their loader without result guidance                    | Accurate uncertain guidance, carried by the existing layout notice across authoring navigation where necessary             |
| Recovery restore/discard                           | Synchronous state replacement, existing recovery dialog, editor-ready control guard | No network-style spinner added to synchronous choices; existing input/recovery behavior retained                           |
| Initial document/Access navigation                 | App may not yet be mounted                                                          | Outside the existing in-app indicator's lifetime; separate structural/authentication work, not implemented here            |
| Explicit logout                                    | Existing exclusive global overlay and verified departure/retry                      | Existing lifecycle retained, shared 200ms visual delay, no minimum departure timer                                         |

Each overlay's accessible status remains outside inert content. List headings
stay outside the list overlay; their existing guards still apply. Navigation
overlays cover the workspace, including its heading, while the session header
is locked separately. Mutation-driven navigation keeps its already-active input
overlay rather than introducing a second workspace overlay.

Region overlays retain their complete bounds, but their status block is sticky
within the region around the viewport center. A long table or mobile card list
must not move the spinner/message below the visible screen. This uses CSS only;
it adds no scroll listeners or timing state. Long-list top/scrolled cases cover
both widths in `loading-viewport.e2e.ts`.

## Acceptance Boundaries

No API/schema/migration, Cloudflare Access login change, remote mutation or
Production deployment is included. Local JWT/Access fixtures do not prove real
Access login/logout or physical-device keyboard acceptance. The timing policy
does not claim to optimize actual network latency.
