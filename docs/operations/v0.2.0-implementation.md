Use superpowers:requesting-code-review for those reviews and the final whole-branch review. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver authenticated Admin post management with explicit saving,
publication, safe Markdown editing, revision protection, and new-post input recovery.

**Architecture:** Build the shared contracts and local D1 persistence first,
then authenticated API handlers, client mutation orchestration, and Admin pages.

Zod, Milkdown/Crepe, Vitest, and Playwright; use the repository's pnpm toolchain.

## Selected Execution and Review Method

Selected on 2026-10-07: the primary agent implements all tasks sequentially;
a separate reviewer agent reviews each completed task before the next begins.
This user-selected workflow adds per-task review to inline execution rather than
dispatching a new implementer for every task.

interfaces, the complete task diff, test results, and recorded implementation
decisions. Review checks both design compliance and code quality. The primary
agent assesses findings, fixes substantive defects, and runs affected tests;
the reviewer verifies the fixes before the task's review gate closes. Record
minor deferred findings with rationale and carry them into the final review.
An unresolved substantive finding is not a completed task; resolve it or report
the blocker before building dependent work on it.

## Global Constraints

- v0.2.0 delivers Admin only. Public endpoints/UI, summary extraction, media,
  permanent deletion, and generated OpenAPI remain deferred.
- Use one `posts` entity, explicit save/publication, and server-side revision
  preconditions. Creation starts at revision `1`; actual changes increment it.
- New-post input recovery uses one localStorage copy per browser/site, expiring
  after seven days (`168` hours) from the last input edit. Existing-post input
  recovery, IndexedDB, and creation-request keys/tables are excluded.
- Block editor input and actions throughout mutation requests, their automatic
  retries, and outcome-recovery reads. Creation has no automatic retry.
- Validate writes and migrations only on local D1. Candidate Version URLs are
  read-only on the server and share production D1.
- Use Milkdown first. Add external rendering/sanitization tools only after
  documenting a demonstrated gap and the selected configuration.
- Follow the agreed layout, including desktop maximum `1024px`, mobile cards,
  filters below the heading/content separation, and groups of five page numbers.
  Exact visual styling and gaps remain provisional.
- Keep existing unrelated code and pre-existing document changes. Do not drop
  the example `task` table or redesign CI/CD as incidental cleanup.
- Implementation follows plan review; deployment and remote migration follow
  the existing release authorization and verification procedure.

## Review Focus

1. An unchanged body must retain its original Markdown even when the editor
   serializer would normalize it; title-only saves omit `body` (Tasks 7 and 10).
2. A committed mutation with a lost response must not trigger an automatic
   duplicate creation or a revision-only overwrite (Tasks 6 and 10). Manual
   inspection remains the creation policy, not a duplicate-free guarantee.
3. Restoring a browser copy must not refresh its expiry or submit it to the server
   (Tasks 8 and 10).
4. Client navigation/remounting must keep the initial document's CSP style nonce
   usable by nested CodeMirror editors without adding unsafe CSP exceptions
   (runtime/header tests in Task 7; actual-page integration in Tasks 9 and 10).
5. Concurrent deletion/restoration and a shrinking last page must retain the
   correct scope, revision behavior, filter, and page size (Tasks 4, 5, and 9).

### Task 6: Client Mutation and Outcome-Recovery Controller

**Change targets:** Create `src/lib/admin/mutations.ts` and `mutations.spec.ts`.

**Interfaces:** Define a `MutationRequest` discriminated union for `create`,
`save`, and `PostCommand`; each existing-post variant carries `id` and its
validated original input. `MutationResult` is a union of `confirmed`, `observed`,
`conflict`, `rejected`, and `unresolved`, retaining the immutable request and
known post ID. `rejected` carries a definite application rejection and its error;
`unresolved` does not claim the request failed. Confirmed DELETE carries no detail
body; its request retains the known ID. Do not parse a `204` response as JSON.
`runMutation(request: MutationRequest, fetcher: typeof fetch): Promise<MutationResult>`
consumes Tasks 3/5. `observed` carries current `AdminPost` but never claims that
the original request succeeded. Create confirmation carries the created row.

- [x] Write fake-timer/fetch tests for one existing-post retry on network/timeout
      or `502/503/504`, no retry on `500` or ordinary conflict, immutable payload,
      lost-response/retry-conflict GET comparison, failed/different reads, and DELETE
      outcome inspection. Anchor: uncertain create sends exactly one POST.
      Verify observed matches do not produce a confirmed-success notification.
      Distinguish validation/auth/state rejection from uncertain transport outcomes;
      test empty-body `204` confirmation without a JSON parsing failure.
- [x] Run `pnpm run test:unit --run src/lib/admin/mutations.spec.ts`; expect the
