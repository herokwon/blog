# v0.2.0 Admin Acceptance and Release Readiness

## Scope and environment

Task 11 checks the implemented Admin contracts in
[Admin validation](admin-validation.md) against the current release branch,
including the SvelteKit 3 dependency migration in PR #40. Public interfaces,
media, permanent deletion, OpenAPI generation, and remote database changes remain
outside this task. The example `task` table is retained.

Local evidence uses Windows, Node 26.11.1, pnpm 12.4.1, Playwright Chromium,
and the compiled production Worker with isolated Miniflare D1. The fixture signs
real RS256 JWTs and substitutes only the external JWKS response; it does not
contact Cloudflare or use the production D1 ID. Existing browser suites run at
1280px and 390px. Touch emulation is distinguished from physical mobile hardware.

## Migration and scope audit

The sole initial migration `drizzle/0000_wealthy_kinsey_walden.sql` creates
`posts` and the example `task` table. It does not drop or alter tables and retains
the earlier `task` column contract. Because both CREATE statements lack
`IF NOT EXISTS`, a previously created unmanaged `task` or `posts` table would
conflict with first application; do not infer safe production application from
fresh local databases. Post defaults, CHECK constraints, indexes and reserved slugs are verified
by migrated SQLite tests; the compiled Worker additionally exercises actual
local D1 SQL and collision behavior. Remote migration history and production
data remain uninspected prerequisites, not claims of compatibility with an
unknown deployed schema. Review the current remote state during release work.

No Public read API/UI, autosave, preview, permanent deletion, media, generated
OpenAPI, creation deduplication, existing-post persistent recovery or database
cleanup is added. Admin uses the Milkdown reading projection with original source
retained and application URL/Markdown guards. No external HTML renderer or unsafe
CSP exemption is required. The known Kit announcer inline style stays blocked;
only its exact hash is excluded from test console-error reporting, while the
shared stylesheet supplies its visually hidden presentation.

## Release checklist

1. Complete physical mobile checks above and record limitations before claiming
   unrestricted mobile support. Keep all remote write testing excluded.
2. During separately authorized release preparation, set package version to
   `0.2.0` (currently `0.1.0`) using the established release procedure. Re-run CI
   and obtain the candidate uploaded for the final `release/v0.2.0` head.
3. Match the candidate tag to that head, annotation to `release/v0.2.0`, and
   recorded Version ID/URL to the upload. Any new head requires a new candidate.
4. On that exact candidate, record deployed authentication/authorization and
   direct mutation rejection. Candidate URLs share production D1; never create
   test posts or apply migrations merely to make pre-promotion reads pass.
5. Review production migration history, SQL, current Worker compatibility and
   recovery version. Missing post schema blocks candidate read verification;
   record it as an unresolved prerequisite until the authorized migration.
6. Open promotion with title ``release: `v0.2.0` `` and a real merge commit.
   Follow [CI/CD operations](ci-cd.md) for exact candidate selection, tag checks,
   production migration and Worker/trigger promotion. Task 11 does not authorize
   this promotion or manual remote migrations.
7. After schema/deployment success, perform candidate post reads and production
   Admin/logout checks. Record source SHA separately from the main merge SHA,
   actual deployed Version ID, migration result, workflow URL and observed results.
   A successful workflow alone is insufficient application evidence.
8. If migration/deployment is partial or fails, inspect actual D1/version state
   before retrying. Worker rollback does not undo migrations; select only a
   current-schema-compatible version and follow the existing recovery procedure.
